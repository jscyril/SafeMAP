Research Prototype Documentation

SafeMAP translates a C function only when it can prove the Rust matches.

SafeMAP is a research prototype for migrating C to safe Rust. It plans a safe, testable Rust interface for each C function, synthesizes the function by an exact rule or a plan-guided LLM request, and accepts it only if it contains no unsafe and matches the original C function under AddressSanitizer and UndefinedBehaviorSanitizer. Every other function is refused with a recorded reason.

What SafeMAP Is

SafeMAP stands for Safe Migration through Analysis-Guided Planning. It is built for research, not production deployment. It asks a narrow question: which C functions can be migrated to safe Rust with per-function evidence that the Rust behaves like the C, and what stops the rest?

SafeMAP does

  • analyze every C function with libclang (pointer roles, allocation, calls, globals);
  • refuse a function before translation when no safe, testable Rust interface exists;
  • synthesize planned functions by exact rules, or by a plan-guided LLM request with compiler-feedback repair;
  • test each accepted function against the original C on up to 1,000 generated inputs, with the C side under ASan and UBSan;
  • record a reason for every function it does not accept;
  • score C2Rust and LLM baselines under the same acceptance policy.

SafeMAP does not

  • translate whole C projects;
  • count reduced unsafe as success;
  • emit unsafe Rust for functions it cannot translate safely;
  • claim formal equivalence (differential testing is evidence, not proof);
  • replace manual review for complex systems code.

Research Claim

The v2 evaluation supports this claim:

Per-function, oracle-checked migration of C to safe Rust is feasible on production C libraries but covers about a tenth of their functions. The planned interfaces are what make LLM translations checkable: the same model produced 1–2 checkable units from the C sources alone and 28–31 when told the planned interfaces. Most functions are refused before translation because pointer ownership or aliasing cannot be resolved statically or because a C type has no safe Rust interface.

What SafeMAP does not claim

  • full automatic C-to-Rust migration;
  • formal equivalence of accepted functions;
  • that SafeMAP's repair loop is the source of the gain (ablations credit interface planning);
  • results on large or multi-file projects, or with other LLMs.

How strong is the acceptance check?

Single-operator mutants of every accepted function were re-tested with 300 inputs from a new seed. The check rejected 164 of 177 non-equivalent compiling mutants (92.7%). The 13 survivors are 12 input gaps (the bug is reachable only on a few specific values) and 1 observation gap.

Ablations (development data)

On the three v1 libraries (142 units), the full system accepted 22. Removing safe-signature planning dropped this to 2 and removing idiom plans to 3; withholding analysis facts from the prompt or removing compiler-feedback repair changed nothing.

History: the first frozen evaluation (v1, on inih, cJSON, and libcsv) accepted 0 of 142 units because of six implementation defects. Those libraries became development data, and v2 was run on newly selected libraries under a new protocol.

Architecture

Every configuration, SafeMAP and baselines alike, is scored by the same per-unit acceptance policy. Baseline output is never counted as a SafeMAP success.

Pipeline Stages

1

Analysis

Recovers compile information and analyzes every function with libclang: signatures, pointer roles (read, write, index, length pairing, nullability), allocation, calls, globals, and unsupported constructs.

2

Translation units

Groups mutually recursive functions into units and orders units by dependency.

3

Screening

Classifies each unit; mutable global state or unresolved pointer ownership makes a unit requires_manual_refactor.

4

Interface planning

Plans a safe Rust signature for each candidate. Any C type with no safe, testable mapping refuses the unit; no signature is fabricated.

5

Synthesis

In dependency order: an exact deterministic rule when one applies, otherwise a plan-guided LLM request with up to three compiler-feedback repairs.

6

Validation

Checks the crate, then runs a differential test per unit against the original C under ASan and UBSan, and records an outcome for every unit.

Acceptance Policy

A translation unit is a C function, or a group of mutually recursive functions. SafeMAP accepts a unit if and only if all of the following hold:

  1. it was admitted to the crate: it has the planned signature, contains no unsafe, raw pointers, extern blocks, or placeholders, and compiles together with the units already admitted;
  2. the final crate compiles under #![forbid(unsafe_code)] and its tests pass, and Clippy reports no error in the unit or in a unit it calls (with per_unit_clippy; otherwise Clippy must pass for the whole crate);
  3. its public interface exposes no raw pointer types; and
  4. its per-unit differential test passes.

A skipped or inapplicable check never counts as a pass.

The per-unit differential harness

  • Inputs come from a fixed seed and include integer literals mined from the C body and their neighbors.
  • Slice and array arguments are exact-size heap buffers, so an out-of-bounds read in C is caught by ASan.
  • The C side runs under ASan and UBSan with -fno-sanitize-recover=all; the Rust side is built with overflow checks.
  • Return values and every value written through a mutable parameter are compared exactly (floating point by bit pattern).
  • An input on which C has undefined behavior is excluded, not used as an expected output. A unit needs at least 50% defined inputs.
  • A defined C abort or exit must be matched by a Rust panic.

Screening Categories

Screening decides, before any translation, whether SafeMAP should try a unit. Units outside the first two categories are refused with the recorded reason.

Category Meaning Translated?
safe_translatable Can be translated without major API change. Yes, if an interface is planned
safe_translatable_with_api_change Can be translated safely with Rust-native API changes. Yes, if an interface is planned
requires_safe_wrapper Would need unsafe internals hidden behind a safe wrapper. No
requires_manual_refactor Unresolved pointer ownership or aliasing, or mutable global state. No
unsafe_required Needs raw memory operations, pointer casts, or FFI. No
unsupported Unions, function pointers, inline assembly, and other unhandled constructs. No

A candidate can still be refused at planning (type_mapping_unresolved) when a type has no safe, testable mapping: opaque void * or FILE *, pointer-to-pointer, returned aliasing pointers, or structs whose pointer fields have unresolved ownership.

Supported C Idioms

The planner maps these C patterns to safe Rust interfaces. Deterministic rules synthesize the simplest cases; others go to the plan-guided LLM.

Pointer-length arrays

int *arr, int len becomes &[i32] or &mut [i32].

Output parameters

void get(int *out) becomes a returned value or tuple.

Error code plus output

int parse(..., int *out) becomes Result<i32, i32>.

Nullable pointers

if (p == NULL) patterns become Option<&T>.

Scalar structs

A struct pointer used only for scalar-field access becomes a Rust struct of those fields.

Manual allocation

Simple owned allocations become Box<T>; simple buffers become Vec<T>.

C strings

Simple const char * inputs used with strlen become &str.

Scalars and booleans

Scalar expressions, reductions, bit idioms, and integer comparison returns as bool.

The primary metric is the number of fully safe accepted units (fully_safe_accepted_units). Every other unit gets one recorded outcome.

C2Rust Baseline

C2Rust 0.22.1 runs in a pinned Docker container with LLVM 14 and is scored under the same acceptance policy. Its output keeps C's raw pointers and unsafe operations, so no C2Rust unit met the policy on the held-out libraries.

Known issue: on parson, sds, and printf, C2Rust's output does not compile with the pinned rustc, because its va_list handling and packed-struct field references are rejected by current Rust. SafeMAP records this as a baseline failure.

LLM Synthesis and Repair

When no deterministic rule applies, SafeMAP sends the LLM one request per unit, through an OpenAI-compatible client. The request contains the C function, the macros, enums, and constant tables it references, the Rust definitions of planned structs, the signatures of already-accepted callees, the analysis facts, and the migration plan, and asks for exactly the planned signature.

Admission

  • No unsafe, raw pointers, extern blocks, or placeholders such as todo!().
  • The planned signature, unchanged.
  • Compiles with the units already admitted; otherwise the compiler diagnostics are returned for up to three repairs.

LLM baselines

  • One-shot LLM (llm_only): one request per project with the C sources, the planned public signatures, and the planned struct definitions. No analysis facts, plans, rules, or repair.
  • Plain LLM (amendment 2): the same request without the planned signatures and structs (scripts/run_plain_llm_baseline.py).

A provider outage stops the run instead of being scored as a failure.

Reproducing the Paper

  1. Download the replication package from Zenodo (source zip and raw results).
  2. Regenerate every manuscript table from the archived result rows: 
    python3 scripts/generate_v2_manuscript_tables.py \
    reports/publication/v2/heldout reports/publication/v2/development out/
  3. Re-score the archived held-out runs under amendment 3 (no API key needed; with the flag off it must reproduce every archived result): 
    python3 scripts/rescore_per_unit_clippy.py OUT_DIR
  4. Measure the acceptance check on a completed run: 
    python3 scripts/harness_mutation_check.py RUN_DIR
  5. Re-run the evaluation from scratch with the commands in Running SafeMAP (needs a Gemini API key). LLM output can differ between runs; the paper reports three.

Limitations

SafeMAP is intentionally conservative. Refusal is a valid outcome when static evidence is insufficient.

  • Ten small libraries with one production file each do not represent large or multi-file projects.
  • One low-cost model and three runs were used; the size of SafeMAP's margin over the one-shot baseline is not established.
  • Differential testing on generated inputs is evidence, not proof; about 7% of non-equivalent mutants survive, mostly where only a few specific inputs reach a branch.
  • Excluding inputs with undefined C behavior removes only what the sanitizers detect.
  • The planner does not yet model borrowed returns, owned types for opaque handles, or explicit contexts for global state.
  • Amendments 1–3 were decided after results were seen; the sealed numbers are reported beside them.
  • Planner changes informed by the current corpus must be evaluated on newly selected libraries.

Troubleshooting

--config: expected one argument

The shell split the command after --config. Use a backslash for multiline commands. 

python -m safemap.cli run \
  --input examples/output_parameter \
  --output results \
  --config safemap.example.yaml

One lint error rejects a whole crate

With per_unit_clippy: false, any Clippy error fails every unit in the crate (crate_validation_failed). Set validation.per_unit_clippy: true to reject only the unit that contains the error and its callers.

Missing LLM API key

Set the environment variable named by llm.api_key_env. For local OpenAI-compatible servers such as Ollama, use a placeholder value such as OLLAMA_API_KEY=dummy if the server does not enforce authentication.

LLM quota or authentication failures

Transient provider errors are retried with backoff. A request still refused after the retries stops the run rather than scoring a failure; resume with --resume after the quota resets.

C2Rust cannot find libclang-cpp.so.14

Use the Docker image, or set SAFEMAP_C2RUST_LIB_DIR or LIBCLANG_PATH to the LLVM 14 library directory. If headers fail to resolve, also set SAFEMAP_C2RUST_RESOURCE_DIR.

Glossary

Translation unit
A C function, or a group of mutually recursive functions, translated and accepted as one.
Fully safe accepted unit
A unit that meets every condition of the acceptance policy, including the per-unit differential test.
Migration plan
A JSON artifact with the planned safe Rust signature, idioms, and constraints for a unit.
Refusal
A unit SafeMAP declines to translate or accept, recorded with its reason.
Differential testing
Running the original C and the generated Rust on the same inputs and comparing every output.
C oracle
The original C function, run under ASan and UBSan; inputs with undefined behavior are excluded.
Sealed protocol
An evaluation plan fixed, with the implementation frozen, before any run on the held-out corpus.
Amendment
A change to the evaluation decided after results were seen, reported beside the sealed results.
Per-unit Clippy
Amendment 3: a Clippy error rejects only the unit containing it and its callers, not the whole crate.
One-shot and plain LLM
Baselines that translate a whole file in one request, with or without SafeMAP's planned interfaces.
