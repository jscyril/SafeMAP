\abstract{Automatic C-to-Rust translators either keep C's pointer conventions
in unsafe Rust or rely on a large language model (LLM) whose output is hard to
trust. \tool translates a C function only when static analysis finds a safe,
testable Rust interface for it, and refuses the rest with a recorded reason.
Planned functions are synthesized by exact rules or a plan-guided LLM request
with compiler-feedback repair. A translation is accepted only if it contains no
\texttt{unsafe}, exposes no raw pointers, and matches the original C function
on up to 1,000 generated inputs, with the C side run under AddressSanitizer and
UndefinedBehaviorSanitizer. On ten held-out C libraries (356 translation units)
selected under a sealed protocol, \tool accepted 12--16 units across three runs.
A declared amendment that re-scores the same outputs with the lint check
applied per unit rather than per crate raised this to 36--37 (10\%). Under the amendment, the same LLM accepted 28--31 units when given
\tool's planned interfaces and 1--2 when given only the C sources; raw C2Rust
accepted none. Most units were refused before translation because pointer
ownership or aliasing could not be resolved statically (127) or because they
use C types with no safe interface (116). The acceptance check rejected 93\% of
non-equivalent compiling mutants of accepted functions. Ablations credit interface
planning, not prompt guidance or repair. Per-function, oracle-checked acceptance is thus feasible on
production C but covers about a tenth of it, and the recorded refusals show
what currently blocks safe automatic migration.}

\keywords{C-to-Rust migration, safe Rust, static analysis, large language
models, differential testing, memory safety}

\section{Introduction}

C remains common in systems software. Its memory model leaves programmers
responsible for preventing buffer overflows, use-after-free errors, null
dereferences, and data races. Safe Rust checks ownership and borrowing at
compile time while retaining low-level control, so migrating C code to safe
Rust is attractive. Translation is difficult because many C idioms have no
direct safe-Rust equivalent: raw pointers, output parameters, manual
allocation, nullable values, and integer error codes all require changes in
representation and interface.

C2Rust preserves C behavior by generating Rust that uses raw pointers and
unsafe operations \citep{c2rust}. Later work reduces this unsafety by static
analysis, ownership inference, refactoring, and LLM rewriting
\citep{emre2021safer,hong2023static,zhang2023ownership,ling2022trust,
nitin2026c2saferrust,mohapatra2026cp2srust}. A second line asks LLMs to
translate directly to safe Rust and checks the result with tests, fuzzing, or
verification
\citep{hong2025typemigrating,zhou2025c2rusttv,eniser2025fluorine,
shetty2024syzygy,zhou2025sactor,yang2025vert,sim2026encrust,
shiraishi2026smartc2rust,farrukh2026safetrans,li2025actor}. These systems
generally aim to translate everything and then measure how much of the result
is safe or correct.

\tool takes the opposite position. It translates a function only when static
analysis finds a safe Rust interface for it, and it accepts a translation only
when that function, on its own, passes a behavioral check against the
original C. Everything else is refused with a recorded reason. The question
is therefore not how much unsafe code remains, but which translated functions
can be trusted: how many functions of real C code can be migrated to safe Rust
with per-function evidence of equivalence, and what prevents the rest. Our results locate \tool's contribution in the planning
step: an LLM told the planned safe interface produces checkable translations,
whereas the same LLM given only the C code almost never does.

An earlier, frozen evaluation of \tool on three C libraries accepted no
units: defects in interface planning, rule matching, and harness construction
each forced the outcome to zero (Section~\ref{sec:history}). This paper
reports the corrected system, evaluated under a new sealed protocol on ten
libraries that were not used during development. We ask five research
questions (RQs):

\begin{itemize}
  \item \textbf{RQ1:} How many translation units of production C libraries
  does \tool accept as safe, behaviorally validated Rust?
  \item \textbf{RQ2:} Why are the remaining units not accepted?
  \item \textbf{RQ3:} How does \tool compare with a one-shot LLM, with and
  without \tool's planned interfaces, with its own rules alone, and with raw
  C2Rust, under one acceptance policy?
  \item \textbf{RQ4:} Which planning components contribute to acceptance?
  \item \textbf{RQ5:} How reliable is the acceptance decision, in terms of
  the harness's ability to reject wrong code and the variation across LLM
  runs?
\end{itemize}

This paper contributes:

\begin{itemize}
  \item a translation pipeline that decides, per function and before any
  translation, whether a safe and testable Rust interface exists, and records
  a reason when it does not;
  \item a per-function acceptance procedure that compares each Rust function
  with the original C function under sanitizers, excluding inputs on which the
  C code has undefined behavior, and whose strength we measure by mutation
  analysis;
  \item a sealed, frozen evaluation on ten held-out libraries showing that
  planned interfaces raise a one-shot LLM from 1--2 to 28--31 accepted units
  and that \tool's per-unit loop accepts 36--37 (under per-unit lint checking,
  a declared amendment), with repeated LLM runs, mutation analysis of the
  acceptance check, and component ablations; and
  \item a breakdown of 356 held-out units by the reason they could not be
  migrated, together with a public artifact for every decision.
\end{itemize}

\section{Background and related work}

\subsection{C2Rust and safer-Rust refactoring}

C2Rust translates C through a mostly syntactic process and is often used as a
baseline or a migration starting point \citep{c2rust}. It preserves many C
constructs with raw pointers and unsafe operations, so much of its output falls
outside Rust's safe subset. Emre et al.\ found that raw pointers cause much of
this unsafety \citep{emre2021safer} and later showed that Rust's borrow checker
rejects many pointer uses that are in fact safe, which limits how far
ownership inference can go \citep{emre2023aliasing}. Studies of hand-written
Rust find that even experienced developers use \texttt{unsafe} widely,
mostly for interoperation and aliasing data structures
\citep{astrauskas2020unsafe}. Hong used static analysis to replace
selected unsafe constructs in C2Rust output, including lock APIs and output
parameters \citep{hong2023static}. C2SaferRust combines C2Rust, static
analysis, and LLM rewriting to reduce unsafe code in translated real-world
programs \citep{nitin2026c2saferrust}. Crown infers ownership models for C
pointers and converts many of them to safe Rust types
\citep{zhang2023ownership}. CRustS and Cp2SRust use different source-to-source
transformations and transpiler designs
\citep{ling2022trust,mohapatra2026cp2srust}. Industry studies and surveys report
that automatic translation still needs substantial manual work and testing
\citep{hong2025cacm,viirola2026feasible}.

\subsection{LLM-based C-to-Rust translation}

LLMs can produce idiomatic Rust, although correctness and type migration remain
open problems. Hong and Ryu studied an LLM translator supplied with candidate
signatures, caller and callee context, and compiler feedback
\citep{hong2025typemigrating}. C2RustTV checks LLM translations with generated
tests and repair loops \citep{zhou2025c2rusttv}. Eniser et al.\ evaluate LLM
translation through cross-language differential fuzzing and find lower success
on more complex real-world samples \citep{eniser2025fluorine}. RustFlow studies
prompting and iterative repair \citep{zhang2026rustflow}. Valenzuela et al.\
examine compiler errors in direct C-to-safe-Rust translation
\citep{valenzuela2026llmcompile}. RustMap combines program analysis and LLM
support at project scale \citep{cai2025rustmap}. Pointer knowledge graphs
annotate code dependency graphs with ownership, mutability, and nullability
facts to guide LLM translation of whole projects \citep{yuan2026pkg}, and
His2Trans mines interfaces and idioms from earlier migrations of the same
codebase \citep{wang2026his2trans}. Both supply the LLM with interface
knowledge, which our results identify as the decisive input.

Several recent systems validate LLM translations against the C program.
SmartC2Rust and SafeTrans repair translations iteratively from compiler errors
and observed behavioral differences \citep{shiraishi2026smartc2rust,
farrukh2026safetrans}. ACToR pairs a translator agent with an agent that
builds differential fuzzers between the C and Rust binaries
\citep{li2025actor}, and TRAIL refines translation insights against executable
counterexamples \citep{wang2026trail}.
Syzygy translates units in dependency order and tests each one against its C
counterpart with LLM-generated inputs \citep{shetty2024syzygy}. SACTOR first
produces interface-preserving Rust that may use \texttt{unsafe}, then refines
it to idiomatic safe Rust, and checks both stages with end-to-end tests linked
to the C code through the foreign-function interface (FFI) \citep{zhou2025sactor}.
VERT checks a readable LLM translation against a WebAssembly (Wasm)-derived oracle
with bounded model checking or property-based testing \citep{yang2025vert}.
ENCRUST wraps LLM translations in shims that preserve the application binary interface (ABI) and removes the
remaining unsafe code with an agent \citep{sim2026encrust}, and Reboot
translates whole interpreters to safe Rust through feature milestones with
occasional user intervention \citep{wang2026reboot}. CRUST-Bench supplies 100
C repositories with hand-written safe-Rust interfaces and tests
\citep{khatry2025crustbench}; those interfaces play the role that \tool's
planned signatures play here.

Table~\ref{tab:related} places \tool among these systems. \tool differs in
three ways. It decides per function, before translation, whether a safe
interface exists, and records a reason when it does not instead of emitting
\texttt{unsafe} code. Its oracle is the original C function itself, run under
AddressSanitizer (ASan) and UndefinedBehaviorSanitizer (UBSan), and inputs on which C has undefined behavior are excluded
rather than used as expected outputs. And acceptance is per function, so one
failing unit does not hide the others. The cost of this conservatism is
coverage, which Section~\ref{sec:results} reports.

\subsection{Undefined behavior and the C oracle}

Differential testing compares two implementations on the same inputs and
treats any disagreement as a defect \citep{mckeeman1998differential}. It needs
a trustworthy oracle. A C execution with undefined
behavior does not define an expected output. ASan and UBSan detect many such
executions \citep{serebryany2012asan,clangubsan}; \tool runs every C oracle
execution under both and discards inputs on which either reports an error.
Miri can detect undefined behavior in Rust \citep{jung2026miri}, but generated
code that contains no \texttt{unsafe} cannot exhibit it, so \tool does not run
Miri.

\section{SafeMAP design}

\subsection{Acceptance policy}
\label{sec:acceptance-policy}

A translation unit is a C function, or a group of mutually recursive
functions. \tool accepts a unit if and only if all of the following hold:

\begin{enumerate}
  \item it was admitted to the crate: it has the planned signature, contains
  no \texttt{unsafe}, raw pointers, \texttt{extern} blocks, or placeholders,
  and compiles together with the units already admitted;
  \item the final crate compiles under \texttt{\#![forbid(unsafe\_code)]},
  and its tests and Clippy pass (under amendment 3,
  Section~\ref{sec:protocol}, Clippy must report no error in the unit or in a
  unit it calls);
  \item its public interface exposes no raw pointer types; and
  \item its per-unit differential test passes (Section~\ref{sec:harness}).
\end{enumerate}

A skipped or inapplicable check never counts as a pass. A unit whose callee
was not admitted is recorded as \texttt{dependency\_missing}.

\subsection{Pipeline}

Figure~\ref{fig:safemap-pipeline} shows the pipeline. For each C project,
\tool:

\begin{enumerate}
  \item recovers compile information and analyzes every function with
  libclang: signatures, pointer roles (read, write, index, length pairing,
  nullability), allocation, calls, and unsupported constructs;
  \item groups mutually dependent functions into units and orders them by
  dependency;
  \item screens each unit (\texttt{candidate\_safe},
  \texttt{manual\_refactor\_required}, \texttt{unsafe\_required},
  \texttt{unknown}); mutable global state makes a unit
  \texttt{manual\_refactor\_required};
  \item plans a safe Rust signature for each candidate. The planner reports
  every C type it cannot map to a safe, testable Rust type: opaque
  \texttt{void *} or \texttt{FILE *}, pointer-to-pointer, returned aliasing
  pointers, and structs whose pointer fields have unresolved ownership. A unit
  with any such issue is refused at planning; no signature is fabricated. A
  struct pointer may be planned as a Rust struct of the struct's scalar fields
  when every use of the pointer in the unit is a scalar-field access, a null
  test, or an argument to a function that satisfies the same condition;
  \item synthesizes each planned unit in dependency order, by an exact
  deterministic rule when one applies and otherwise by a plan-guided LLM
  request followed by up to three compiler-feedback repairs; and
  \item validates the crate and each unit against the acceptance policy.
\end{enumerate}

\subsection{Deterministic rules and plan-guided synthesis}

Deterministic rules cover scalar expressions, boolean and bit-reversal
idioms, pointer-length and fixed-size arrays, scalar structs and field access,
dependency-ordered internal calls, output parameters, return-code plus
output-parameter to \texttt{Result}, nullable pointers, reductions, simple C
string lengths, and simple allocation-to-\texttt{Vec} and \texttt{Box}
patterns. A rule that renders a single expression applies only when the whole
function body is that statement and the expression references only
parameters and called functions.

When no rule applies, \tool sends the LLM the C function, the macros, enums,
and constant tables it references, the Rust definitions of the planned
structs, the signatures of already-accepted callees, the analysis facts, and
the migration plan, and asks for exactly the planned signature. The response is
admitted only if it passes the policy check and compiles with the units
already admitted; otherwise the compiler diagnostics are returned for up to
three repairs.

Consider the LLVM development helper below. libclang finds two indexed
pointers paired with \texttt{n} and no writes, so the plan maps each
pointer-length pair to a shared slice, and the \texttt{slice\_dot\_product}
rule applies:
\begin{lstlisting}[language=C,basicstyle=\ttfamily\scriptsize]
double loop(float *x, float *y, long n) {
  double acc = 0.0;
  for (long i=0; i<n; ++i) acc += (double)x[i] * (double)y[i];
  return acc;
}
\end{lstlisting}
\begin{lstlisting}[basicstyle=\ttfamily\scriptsize]
pub fn r#loop(x: &[f32], y: &[f32]) -> f64 {
  x.iter().zip(y.iter()).map(|(&a,&b)| (a as f64)*(b as f64))
   .fold(0.0_f64, |s,v| s + v)
}
\end{lstlisting}
The initial value \texttt{+0.0} is necessary: differential testing showed that
\texttt{sum()} can disagree with C on the sign of zero.

\subsection{Per-unit differential harness}
\label{sec:harness}

For each admitted unit, \tool generates inputs from a fixed seed, including
integer literals mined from the C body and their neighbors, and embeds the same
literal tables in a C harness and a Rust harness. Slice and array arguments
are exact-size heap buffers, so an out-of-bounds read in C is caught by ASan
rather than masked. The C harness includes the original translation unit and
runs under ASan and UBSan with \texttt{-fno-sanitize-recover=all}; the Rust
harness is built with overflow checks. Return values and every value written
through a mutable parameter are compared exactly (floating point by bit
pattern, strings byte by byte). An input on which the C oracle stops with a
sanitizer report has no defined behavior and is excluded and counted. A
defined C \texttt{abort} or \texttt{exit} must be matched by a Rust panic. A
unit needs at least 50\% defined inputs; otherwise it is recorded as
\texttt{c\_oracle\_undefined\_behavior}.

\subsection{Baselines}

\emph{Raw C2Rust} translates every project in a pinned container 
(C2Rust 0.22.1, LLVM 14) and is measured under the same policy. 
\emph{Rules only} runs the same pipeline without the LLM. 
In a single request, the \emph{one-shot LLM} baseline receives 
the same work as \tool: the C sources and headers of the project, 
the planned public signatures (with C names preserved), and the Rust struct 
definitions used by those signatures, with private helpers permitted. It does not 
receive any of \tool's analysis facts, plans, rules, or repairs. Once top-level functions 
are made public, its output is scored using the same per-unit harness.
Giving the interfaces isolates what \tool adds beyond interface planning.
The \emph{plain LLM} baseline (amendment 2) measures the planning itself: the
same request without the planned signatures and struct definitions, so the
model sees only the C sources and the safety rules. Its output is scored the
same way; a function with any other signature cannot be called by the
harness and is recorded as \texttt{interface\_mismatch}.

\section{Evaluation methodology}

\subsection{Earlier evaluation}
\label{sec:history}

A first frozen evaluation (protocol v1) ran \tool on inih, cJSON, and libcsv
and accepted 0 of 142 units. Every one of six defects independently forced
that result: the signature planner mapped C types incorrectly; rules fired on
partial matches and emitted template code; struct definitions in headers were
not collected; acceptance was all-or-nothing per project; the C2Rust setup
shadowed libc headers; and the harness covered only scalar shapes. Because the
v1 corpus was inspected while diagnosing these defects, it is used here only
as development data, and the corrected system was evaluated on newly selected
libraries under a new protocol.

\subsection{Protocol}
\label{sec:protocol}

The v2 protocol fixed the selection rule, configurations, model, acceptance
policy, and reporting before any \tool execution on the held-out corpus. A
library qualifies if it is a public Git repository with an Open Source Initiative (OSI)-approved
license, its production code is one \texttt{.c} file plus headers that
compiles against libc alone, the file has 150--3,500 lines, and it was not
used during development. All functions in the file are retained. The protocol
and corpus manifest were sealed and the implementation frozen at commit
\texttt{62cf430} before the corpus was materialized; a materialization script
refuses to run on any other commit. The full test suite passed at the freeze.

Four libraries were selected first: parson, sds, tinyexpr, and microtar.
After their results were seen, we judged four libraries too few and added six
more by the same rule (amendment 1): json-parser, tiny-regex-c, tiny-AES-c,
semver.c, argparse, and printf. Nine candidates qualified in a fresh screen;
six were chosen for domain diversity before any \tool execution on them. The
implementation, configuration, and modes were unchanged. We report the two
rounds separately and pooled. After all results were seen we added one
baseline (amendment 2), the plain LLM described above, run three times with the
frozen implementation by a script that refuses to run if the implementation
or configuration differs from the freeze.

Finally, after all results were seen, we changed how Clippy is applied
(amendment 3). The sealed policy runs Clippy once per crate, so a single lint
error rejects every unit in the crate (Section~\ref{sec:rq1}). Under amendment
3, each Clippy error is mapped to the function that contains it, and only that
unit and the units that call it are rejected; an error outside every unit's
function still rejects the crate. The same rule applies to \tool and to the
LLM baselines. No output was regenerated and no LLM was called: the archived
crate of every held-out run was re-scored with the frozen checks and
differential harness (\texttt{scripts/rescore\_per\_unit\_clippy.py}). With the
change switched off, the re-scoring reproduced the archived result of every
run. Tables report the amended numbers, with the sealed number in parentheses
wherever it differs. The development data and ablations were not re-scored.
Table~\ref{tab:v2-corpus} characterizes the corpus.

\subsection{Configuration}

All LLM configurations, \tool and baseline alike, use Google's
\texttt{gemini-3.5-flash-lite} at temperature zero through its
OpenAI-compatible application programming interface (API), with at most three repairs per unit, 1,000 generated
inputs per unit, and seed 20260728. The evaluation used the provider's free
tier. A request still refused after the client's retries stops the run rather
than being scored as a failure; the run resumes after the quota resets, reusing
every finished (project, configuration) result. Because LLM output can vary
even at temperature zero \citep{ouyang2025nondeterminism}, the LLM configurations were run three times on every
held-out library with identical inputs; the first run is the primary result.
Tool versions: rustc and Clippy 1.99.1, Clang 23.1.3; C2Rust 0.22.1 with LLVM
14 in a pinned container.

\textbf{Use of LLMs in this study.} Apart from the evaluated pipeline's own
calls to \texttt{gemini-3.5-flash-lite}, the authors used LLM assistants during
the research. ChatGPT helped generate the 40 synthetic development
microbenchmarks. ChatGPT and Claude assisted with implementing and testing
\tool, writing the evaluation scripts, and drafting and revising this
manuscript. All AI-assisted code was reviewed by the authors and exercised by
the project's test suite. Every reported number is produced by the committed
scripts from the archived raw results, not written by hand. No LLM selected the
held-out corpus or judged the correctness of a translation.

\subsection{Development data}

Development data comprises 40 authored microbenchmarks, six authored modules,
ten LLVM test-suite programs pinned at commit \texttt{6cdc54e}
\citep{llvmtestsuite}, and the three v1 libraries. Their results informed the
corrections, so they are not evidence of generalization. The component
ablations are run on the v1 libraries with the frozen implementation and are
reported as development data, which keeps the held-out LLM run within the
provider's quota.

\subsection{Mutation analysis}

We performed mutation analysis \citep{jia2011mutation} to see if the per-unit 
check rejects incorrect code. Every accepted function of \tool's held-out 
runs and of its v1-library run, including the functions accepted only under 
amendment 3, was subjected to single-operator mutations (relational, arithmetic, 
logical, boolean, and integer-literal changes). We retained the mutants that compile 
and reran each unit's differential test with 300 inputs from a different seed. 
Each surviving mutant was manually categorized as either an observation gap (the 
harness does not compare the differing output), an input gap (a distinguishing input 
exists but was not generated), or equivalent (no input can distinguish it).

\section{Results}
\label{sec:results}

\subsection{RQ1: Accepted units}
\label{sec:rq1}

Table~\ref{tab:v2-cascade} follows each held-out unit through the pipeline.
In the first run, of 356 units, the screen marked 183 as candidates, \tool
generated Rust for 47, and accepted 37 (10.4\% of all units; 20.2\% of
candidates). Under the sealed crate-level check it accepted 16 (4.5\%). The
original four libraries contributed 28 accepted units and the extension 9.
Accepted units are small leaf functions: tinyexpr's arithmetic, comparison,
and logical operators and its factorial and combinatorics helpers, a string
hash, hexadecimal and UTF-8 helpers, rounding, error strings, version-string
checks, regular-expression character classes, and the AES \texttt{xtime} step.

\input{tables/cascade.tex}

The whole difference between the sealed and amended results comes from
tinyexpr. Its 24 generated units compiled, but two translated constants,
\texttt{pi} and \texttt{e}, keep C's literal digits, which Clippy's
default-deny \texttt{approx\_constant} lint rejects. Under the sealed check,
Clippy runs once per crate, so these two errors rejected all 24 units. Under
amendment 3 they reject only \texttt{pi} and \texttt{e}. Of the other 22
units, 21 matched the C functions on every defined input, and one,
\texttt{negate\_logical\_not}, disagreed with C.

\subsection{RQ2: Why units are not accepted}

Table~\ref{tab:v2-refusals} lists the recorded reasons. Most units never
reach translation. The screen marked 159 functions as needing manual
refactoring. For 127 of them, the analysis could not resolve pointer
ownership or aliasing statically. The other 32 read or write mutable global
state; 30 of these are in parson, whose allocator hooks
\texttt{parson\_malloc} and \texttt{parson\_free} are global function
pointers. 116 functions use a C type for which the planner finds no safe,
testable interface. The most common case (48 functions) is a returned pointer
that aliases caller-owned data, whose lifetime the planner does not model. In
parson and sds the central types (\texttt{JSON\_Value *}, \texttt{sds}) are
opaque handles or point into the middle of an allocation, and \texttt{void *}
and \texttt{char **} parameters are common. 36 functions require unsafe
operations such as pointer arithmetic beyond a known length or casts between
pointer types. Only a small fraction of losses occur after translation: 4
differential-test failures, 4 units whose C oracle had undefined behavior on
most generated inputs, and 2 units with Clippy errors. Two of the undefined-behavior cases show a
limit of signature-level planning: sds's \texttt{sdsll2str} writes up to 21
bytes into a caller buffer, a requirement its signature does not express, so
every generated buffer overflowed. The other two overflow signed arithmetic on
most inputs.

\subsection{RQ3: Baselines}

Table~\ref{tab:v2-baselines} compares the configurations. In the first run
\tool accepted 37 units, the one-shot LLM given the planned interfaces 28, the
plain LLM 1, rules alone 6, and C2Rust none (sealed: 16, 9, 1, 1, and 0).
\tool accepted more units than the interface-given baseline in each of the
three runs, 36--37 against 28--31 (Section~\ref{sec:rq5}). Under the sealed
check the two ranges overlapped (12--16 against 9--15). In the first run the
difference is concentrated in three libraries: tinyexpr (21 against 16), sds,
and tiny-regex-c. Only tinyexpr's gap recurs in all three runs. On the other seven the two configurations are within one unit
of each other, and on parson the baseline is one unit ahead. The plain LLM shows what the planned
interfaces contribute: for four libraries its output used \texttt{unsafe}
code or raw pointers and was rejected outright, and in the other six, of 43 planned
functions, 24 were absent from the output and 12 had other signatures, so
they could not be checked against the C function; 6 were in crates that
failed compilation or Clippy, and 1, in semver, was accepted. \tool used 40 LLM
requests and the one-shot baseline 8 (one per library with planned
interfaces). The one-shot baseline benefits from \tool's interface planning:
without the planned signatures, its output could not be tested function by
function. Raw C2Rust output compiled for seven of ten libraries; for parson,
sds, and printf it failed on the pinned toolchain because its
\texttt{va\_list} handling and packed-struct field references are rejected by
current rustc. Where it compiled, it contained unsafe code and raw-pointer
interfaces throughout, so no unit met the policy.

Table~\ref{tab:v2-ablations} reports the ablations on the v1 libraries.
The full system accepted 22 of 142 units. Removing safe-signature planning

\subsection{RQ5: Reliability of acceptance}
\label{sec:rq5}

\textbf{Mutation analysis.} We first mutated the functions accepted under the
sealed check (first run of all ten held-out libraries, and the v1 libraries).
Of 152 compiling mutants, the per-unit check rejected 135 (88.8\%). Of the 17
survivors, 4 are equivalent: \texttt{>} replaced by \texttt{>=} directly
after an equality test, the same change where both branches yield the same
value on ties, a loop bound that a terminator written just before already
guarantees, and an unreachable \texttt{else}. We then mutated the 21 tinyexpr
functions accepted only under amendment 3, in the same way. The check rejected
29 of their 34 compiling mutants. The 5 survivors, in \texttt{fac} and
\texttt{ncr}, are equivalent: exhaustive checks over the reachable inputs show
that each changes a comparison or starting value without changing any result.
Over both sets, excluding the 9 equivalent mutants, the check rejected 164 of
177 non-equivalent mutants (92.7\%); all 13 non-equivalent survivors are
from the first set.
Twelve survivors are input gaps: they change
behavior only on a few specific values, such as one or two digits in sds's
hexadecimal converter (six mutants), a string of exactly 255 or 256 bytes, or one
error code, which uniformly generated inputs rarely hit. One is an observation
gap: a copy routine's output differs only after the string terminator, which
the harness, like a C caller, does not read. Targeted inputs from the C
function's literals and comparison bounds would close most input gaps.

\textbf{Repeated runs.} Table~\ref{tab:v2-repeats} reports accepted units in
three runs of the LLM configurations with identical inputs. \tool accepted 37,
36, and 36 units, the one-shot baseline 28, 31, and 30, and the plain LLM 1, 1,
and 2 (sealed: 16, 15, and 12 for \tool; 9, 15, and 14 for the one-shot
baseline). Nine of the ten libraries gave the same \tool result in every run,
against six for the one-shot baseline. Under the sealed check most of the
variation came from semver: in one run of each configuration, one generated
function failed a crate-level Clippy check and so rejected every planned unit
of that crate, the same mechanism as tinyexpr. Per-unit Clippy removes this
effect. The accepted sets are therefore stable at the function level, and the
sealed results were sensitive to crate-level failures.

\section{Discussion}

\textbf{Coverage is the limiting factor.} The per-function acceptance check is
feasible on production C and rejects most wrong code, but few functions reach
it. Table~\ref{tab:v2-refusals} is the main finding. The obstacles are
pointer ownership and aliasing that static analysis cannot resolve, returned
pointers into caller-owned data, opaque pointer types, raw memory
manipulation, and, in parson, global allocator hooks. Some of these could be
planned: a pointer returned into an argument corresponds to a borrowed Rust
return such as \texttt{fn f<'a>(s: \&'a str) -> \&'a str}. Others are API
design questions that a function-local translator cannot answer alone. There,
a migration would need to change the library's interface before \tool's
checks apply, for example by turning an \texttt{sds} string into an owned
type.

\textbf{Interfaces matter more than prompts.} On the held-out libraries the
same model accepted 1--2 units from the C code alone and 28--31 when told the
planned interfaces. \tool's per-unit loop added a further 6--9 units in each
run, most of them in one library. On the
development libraries, removing signature planning from the guided loop
reduces it from 22 to 2 units. Withholding analysis
facts from the prompt changed nothing on the v1 libraries. This suggests that LLM translators benefit most from being
told the target interface, which is consistent with CRUST-Bench's use of
hand-written interfaces \citep{khatry2025crustbench}.

\textbf{Refusal as output.} Every refused unit carries a reason and the plan
that produced it. For a migration team this identifies which functions can be
migrated mechanically and which need design work.

\section{Threats to validity}
\label{sec:threats}

\textbf{Sample.} Large applications or multi-file projects are not represented 
by ten small libraries with one production file each. The extension, which 
employed the same rule and frozen code, was chosen after the first four results 
were seen. We report the two rounds separately.

\textbf{Model and variance.} Three runs are insufficient to accurately quantify 
run-to-run variance, and just one inexpensive model was employed. The guided 
loop under per-unit Clippy accepted more than the one-shot baseline in each run, 
but its size is not established because the majority of the margin originates from a 
single library. Following the observation of the other outcomes, the plain LLM baseline 
and amendment 3 were added. Although it cannot alter the units rejected before translation, 
which account for the majority of losses, a stronger model might translate more of the planned 
units. 

\textbf{Oracle.} Differential testing on generated inputs is evidence, not
proof. Mutation analysis shows that 7.3\% of non-equivalent compiling mutants
survive, mainly where only a few specific inputs reach a branch. Excluding inputs with undefined C
behavior removes inputs the sanitizers detect, not all undefined behavior.

\textbf{Post-hoc amendment.} The sealed policy ran Clippy on the whole crate,
so one lint error rejected every unit in it (tinyexpr, and semver in one
repeated run). Amendment 3 removes this, but it was decided after the results
were seen. It changes only how the archived outputs are scored, applies the
same rule to every configuration, and reproduces the sealed results when
switched off. We report the sealed numbers beside the amended ones. A lint
error outside every unit's function still rejects the whole crate.

\textbf{No eligibility labels.} We did not collect independent labels of
which functions could be migrated safely, so we make no claim about the
precision or recall of the screen; refusals are reported as recorded.

\textbf{Toolchain.} C2Rust 0.22.1's output does not compile with the pinned
nightly on three libraries; another toolchain might compile it, but it would
still use unsafe code and fail the policy.

\textbf{Development data.} The development corpora and the v1 libraries
shaped the implementation; results on them are not evidence of
generalization, and the ablations are run on them.

\section{Conclusion}

\tool translates C functions to safe Rust only when it finds a safe interface
and accepts them only when they match the original C under sanitizers, so
every accepted function carries its own evidence of equivalence. On ten
held-out libraries it accepted 12--16 of 356 units across three runs under
the sealed crate-level lint check, and 36--37 when the same outputs were
re-scored with the lint check applied per unit. Under that check, the same LLM
accepted 1--2 units from the C code alone and 28--31 when given \tool's
planned interfaces; rules alone accepted 6 and raw C2Rust 0. These translations can 
be produced and verified thanks to the interface planning, and a minor further gain 
is added by \tool's per-unit loop. The majority of units are rejected prior to translation 
because the function requires unsafe memory accesses, a C type lacks a safe interface, or pointer ownership or 
aliasing cannot be resolved statically. Oracle-checked, per-function migration is therefore possible, 
but it only covers around 10\% of these libraries; its scope is determined by the extent to which a 
C library's interface already has a safe Rust equivalent. Future work should plan borrowed returns for functions that
return pointers into their arguments, generate inputs from the C function's
literals and bounds to close the remaining input gaps, and plan interface
changes such as owned types for opaque handles. These changes should be
evaluated on newly selected libraries, since the present corpus has now
informed the analysis.
